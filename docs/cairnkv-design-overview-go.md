| 项 | 内容 |
|----|------|

## 1. 项目简介

CairnKV 是一个用 Go 实现的**嵌入式、持久化、有序键值存储引擎**。它以 LSM-Tree 为核心，通过“先顺序追加日志、再在内存中整理、最后批量落盘为不可变文件”的方式，把随机写转化为顺序写，并在崩溃后能够恢复到一致状态。

项目名中的 Cairn（石堆路标）取意于其设计：数据被写成一块块不可变的文件，逐层堆叠、合并，形成可靠的“路标”。

### 1.1 项目定位

- **它是存储基座，不是完整数据库。** 只提供有序字节键值语义，不含 SQL、查询优化器、多语句事务。
- **嵌入式优先。** 主要形态是被 Go 程序以库的方式引用；网络服务和远程客户端是独立、可选的上层组件。
- **可被二次开发。** 上层可以通过键编码约定，在其上构建时序、宽列、按 ID 文档等适合有序访问模式的数据结构。

### 1.2 设计目标

| 目标 | 含义 |
|------|------|
| 持久化 | 已确认写入的数据在进程崩溃后不丢失（取决于所选同步档位） |
| 崩溃一致性 | 重启后数据库状态可重建，不出现指向半截文件的元数据 |
| 写优化 | 以顺序追加为主要磁盘写模式 |
| 可度量 | 能量化写放大、读放大、空间放大，支持对照实验 |
| 可扩展 | 通过稳定接口替换策略与后端，并支持上层数据结构复用 |
| 可维护 | 模块边界清晰，核心引擎不依赖网络层 |

### 1.3 明确不做

- SQL 与关系模型
- 多键事务、隔离级别与 MVCC 全量实现
- 自动分片、自动选主与强一致多副本
- 图遍历、列式分析、向量检索等需要专门物理布局的模型
- Web 前端

## 2. 组件与运行形态

CairnKV 由核心引擎和若干独立组件组成，依赖只能单向：

```text
cairnkv-client（远程 SDK）
        │ 网络协议
        ▼
cairnkv-server（网络接入层）
        │ 调用公开 API
        ▼
cairnkv（嵌入式入口 + 公开 API）
        │
        ▼
internal 核心引擎（WAL / MemTable / SSTable / Manifest / Compaction）
```

| 组件 | 职责 | 是否属于存储内核 |
|------|------|------------------|
| 核心引擎 | 持久化、索引、恢复、合并 | 是 |
| 嵌入式入口 | 打开数据目录、生命周期管理、暴露公开 API | 是（薄封装） |
| 网络接入层 | 监听连接、协议编解码、请求调度 | 否，独立组件 |
| 远程客户端 | 连接管理、超时、请求响应匹配 | 否，独立组件 |
| 命令行工具 | 手动读写、压测、恢复演示 | 否，工具 |
| 示例 | 演示在 KV 上构建时序等结构 | 否，仅依赖公开 API |

依赖规则：

1. 核心引擎**不得**引用网络、命令行或示例代码。
2. 网络接入层只能通过公开 API 访问引擎，不能直接操作 WAL 或 SSTable 文件。
3. 示例和上层扩展只能依赖公开 API，不能引用 `internal` 包。

## 3. 功能需求

优先级：**M** 必须，**S** 应当，**C** 可选，**W** 明确不做。

### 3.1 基础数据操作

| 编号 | 需求 | 优先级 |
|------|------|--------|
| F-01 | 键和值均为任意字节序列，引擎不解释值的内容 | M |
| F-02 | 支持写入、读取、删除单个键 | M |
| F-03 | 删除通过墓碑标记实现，旧文件中的历史数据在合并时回收 | M |
| F-04 | 同一键后写覆盖先写，以全局单调递增的序号判定新旧 | M |
| F-05 | 支持按键有序的范围扫描，可设定起止边界和数量上限 | M |
| F-06 | 提供迭代器接口用于扫描，并规定其生命周期与关闭方式 | M |
| F-07 | 支持批量写入，同一批次内的操作要么全部生效、要么全部不生效 | S |
| F-08 | 支持只读快照，读取期间不受后续写入影响 | S |

### 3.2 持久化与崩溃恢复

| 编号 | 需求 | 优先级 |
|------|------|--------|
| P-01 | 每次变更在确认前先记录到预写日志（WAL） | M |
| P-02 | WAL 分两层：物理分块层（每个 chunk 带校验和、长度、片段类型、日志号、已同步偏移）与逻辑记录层（批次起始序号、操作数，以及每个操作的类型、键、值） | M |
| P-03 | 提供三档同步策略：逐次同步（`SyncAlways`）、分组同步（`SyncGroupCommit`，默认）、不同步（`NoSync`，须显式选择，名称不宣称持久性） | M |
| P-04 | 重启时只截断最后一个 WAL 中由崩溃留下的残缺尾部；已同步区域内的任何损坏都必须报错，不得静默截断 | M |
| P-05 | 元数据（MANIFEST）是崩溃后状态的唯一依据，记录当前有效的数据文件集合；当前 MANIFEST 由标记文件指出（取代 `CURRENT`） | M |
| P-06 | 数据文件写完并 fsync 后才登记进元数据；元数据切换通过新建标记文件原子完成（数据文件不经过临时文件重命名） | M |
| P-07 | 未被元数据登记的残留文件，在启动时识别并清理 | M |
| P-08 | 进程独占数据目录，禁止两个实例同时打开同一目录 | M |

### 3.3 存储结构与读路径

| 编号 | 需求 | 优先级 |
|------|------|--------|
| S-01 | 内存表接收新写入，达到阈值后冻结并刷为不可变有序文件 | M |
| S-02 | 数据文件分块存储，配有块索引，可快速定位 | M |
| S-03 | 每个数据文件带布隆过滤器，减少不存在键的磁盘访问 | M |
| S-04 | 数据块带校验和，读取到损坏数据时明确报错 | M |
| S-05 | 读取顺序：活动内存表 → 冻结内存表 → 数据文件（由新到旧） | M |
| S-06 | 块缓存，限定容量，缓解重复读取 | S |
| S-07 | 数据压缩（按块，默认 Snappy） | M |

### 3.4 后台合并

| 编号 | 需求 | 优先级 |
|------|------|--------|
| C-01 | 实现分层（Leveled）合并策略，作为第一期默认 | M |
| C-02 | 合并时丢弃被覆盖的旧版本，并在安全条件下回收墓碑 | M |
| C-03 | 合并结果先落盘，再原子切换元数据，最后删除旧文件 | M |
| C-04 | 合并不能让前台写入长时间停顿；积压时通过限速或拒绝写入施加背压（每次写入可选阻塞或返回 `ErrWriteStall`） | M |
| C-05 | 合并策略以接口形式存在，可替换 | M |
| C-06 | 按文件大小分层（size-tiered）合并策略（第一期不做，接口预留） | C |

### 3.5 网络接入层（独立组件）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| N-01 | 提供 TCP 二进制协议：写入、读取、删除、范围扫描、心跳 | M |
| N-02 | 协议带版本号、请求标识、错误码和最大帧限制 | M |
| N-03 | 请求处理与磁盘操作解耦，网络协程不因磁盘阻塞而拖垮整体 | M |
| N-04 | 写入队列有界，过载时返回明确错误 | M |
| N-05 | 远程客户端 SDK：连接复用、超时、异步请求、请求响应匹配 | M |
| N-06 | 明确客户端超时语义：超时不代表写入一定失败，重试策略需按幂等性区分；由协议层实现（幂等请求 ID + 可查询提交状态），引擎不提供带超时的写入 | S |
| N-07 | 基础健康检查与指标输出 | S |

### 3.6 可观测性与实验支撑

| 编号 | 需求 | 优先级 |
|------|------|--------|
| O-01 | 输出写入/读取吞吐及延迟分位数 | M |
| O-02 | 统计并输出写放大、读放大、空间放大 | M |
| O-03 | 记录 WAL 同步次数、刷盘次数、合并次数与耗时 | M |
| O-04 | 记录启动恢复耗时与重放记录数 | S |
| O-05 | 内置与内存参考实现对拍的随机测试 | M |
| O-06 | 提供故障注入点：如日志写入后崩溃、数据文件写完但元数据未更新时崩溃 | M |

## 4. 非功能需求

### 4.1 正确性与语义

- 单键操作原子：恢复后要么看到完整的新值，要么保持旧值。
- 逐次同步档（`SyncAlways`）：确认返回之前，该写入已通过同步调用刷盘。
- 分组同步档（`SyncGroupCommit`，默认）：确认发生在包含该批次的那一次组提交 fsync 成功返回之后；文档必须明确该语义与延迟代价。
- 不同步档（`NoSync`）：返回时只保证写入已进入日志，不保证持久；崩溃可能丢失这些写入，但恢复结果仍是已提交批次的某个前缀，不会出现中间缺口。
- fsync 失败后引擎进入毒化状态：之后所有操作返回 `ErrEnginePoisoned`，绝不把未持久化的写入报告为成功。
- 范围扫描结果按键升序，不出现同一键的重复可见版本。

### 4.2 性能（实验性目标）

不预设绝对数字，而是要求可对比、可复现：

1. 顺序追加 vs 随机覆盖写的吞吐对比
2. 逐次同步 vs 分组同步的吞吐与尾延迟对比
3. 有无布隆过滤器时点查读放大对比
4. 合并策略对写放大与空间占用的影响

### 4.3 资源控制

- 内存表和块缓存有硬上限。
- 后台合并、刷盘并发度可配置。
- 单进程运行，不依赖外部服务。

### 4.4 可移植性

- 首要平台：Linux；macOS 用于开发。
- 平台相关代码（内存映射、目录同步等）集中隔离，其余代码保持可移植。
- 需要专门验证：`fsync` 语义在不同文件系统上的差异。

## 5. 可扩展性设计

### 5.1 扩展的两个层次

| 层次 | 扩展什么 | 扩展方式 |
|------|----------|----------|
| 引擎内部策略 | 合并策略、同步档位、缓存策略、I/O 后端、内存表实现 | 依赖**接口注入**，通过配置选择实现 |
| 引擎上层数据结构 | 时序、宽列、按 ID 文档、有序集合等 | 依赖**键编码约定 + 公开 API**，不改动引擎 |

### 5.2 内部策略：接口注入

以下能力在设计时抽象为接口，第一期只提供一种默认实现：

| 抽象 | 职责 | 默认实现 | 未来可替换为 |
|------|------|----------|--------------|
| 合并策略 | 决定何时合并哪些文件 | 分层（Leveled） | 按大小分层（size-tiered）、混合（hybrid） |
| WAL 同步策略 | 决定日志何时刷盘 | 逐次 / 分组（默认）/ 不同步 | 定时刷盘、自适应分组 |
| I/O 后端 | 文件打开、追加、读、刷盘、目录同步、加锁 | 标准文件接口（公开包 `vfs`） | 内存实现（测试用）、故障注入包装、直写方式 |
| 内存表 | 有序内存结构 | 跳表 | 其他有序结构 |
| 键比较器 | 定义键的排序规则 | 字节序 | 自定义排序（谨慎） |
| 缓存 | 块缓存策略 | 分片 CLOCK-Pro | 其他淘汰策略 |
| 过滤器 | 判定键是否可能存在 | 缓存行分块布隆过滤器（10 bits/key） | Ribbon、Binary Fuse 等 |

约束：

1. 替换任何策略都不得破坏“确认写入必已持久化”的语义。
2. 接口保持小而稳定，避免暴露内部数据结构。
3. 键比较器一旦选定，不得随意更改：它决定文件内的排序，更换会使已有数据失效，所以需要记录在元数据中并在启动时校验。

### 5.3 上层扩展：在有序 KV 上构建结构

引擎只保证“字节序有序 + 范围扫描”，上层通过**键设计**获得不同访问模式。

| 目标结构 | 映射思路 | 需要引擎提供的能力 |
|----------|----------|--------------------|
| 时序数据 | 实体标识 + 可排序时间戳 → 样本 | 范围扫描 |
| 宽列式行 | 行键 + 列名 → 单元格 | 范围扫描、可选过期 |
| 按 ID 的文档 | 文档 ID → 序列化文档 | 点查 |
| 有序集合 | 集合 ID + 分数 + 成员 → 空值 | 范围扫描、批量原子写（修改分数需要） |
| 二级索引 | 索引值 + 主键 → 空值 | 批量原子写 |

原则：

- **命名空间隔离。** 上层结构使用固定前缀区分类型，避免不同用途的键互相污染。
- **保序编码。** 复合键的各字段编码后必须保持期望的排序关系，边界要有明确分隔。
- **原子性。** 需要同时修改数据与索引时，必须使用批量写；否则只能声明“索引可重建”。
- **诚实的边界。** 图遍历、列式聚合、向量检索不属于此底座适用范围。

### 5.4 扩展点稳定性等级

| 等级 | 含义 | 对象 |
|------|------|------|
| 稳定 | 版本内不破坏兼容 | 公开 API、网络协议、数据目录格式版本 |
| 实验 | 可能调整 | 策略接口、指标输出格式 |
| 私有 | 随时可改 | `internal` 下的一切 |

文件格式必须带版本号与魔数。格式升级需要明确的迁移或拒绝打开策略，避免静默读取错误。

### 5.5 演示扩展

只做**一个**上层示例（建议：时序数据层），用于证明底座可复用，并通过对比不同键编码方案说明“布局影响性能”。示例只依赖公开 API。

## 6. 工程与文件组织规范

依据 Go 官方对模块布局的建议：私有包放入 `internal/`，多个可执行程序放入 `cmd/<名称>/`，并由小的 `main` 装配 `internal` 中的包；`internal` 由编译器强制限制外部导入。 [web:323][web:331]

### 6.1 仓库结构

```text
cairnkv/
├── go.mod
├── README.md
├── LICENSE
├── justfile                 # 常用命令：构建、测试、Linux 容器测试、门禁
├── cairnkv.go               # 公开入口（package cairnkv）：Open / DB 接口 / Options
├── options.go               # 公开配置类型
```

说明：

- 根目录包 `cairnkv` 是**唯一稳定级的公开 API**；`vfs` 是实验级公开包，用于注入内存实现与故障注入；其余实现细节放在 `internal/`。
- 是否使用 `pkg/` 目录并非 Go 官方要求；`golang-standards/project-layout` 也明确说明它不是 Go 团队定义的官方标准。 [web:329] 本项目公开 API 放根目录，不额外引入 `pkg/`。
- `server`、`client`、`proto` 是独立包，若日后希望它们成为独立模块，可以拆分为单独的 `go.mod`；第一期保持在同一仓库、同一模块。

### 6.2 依赖方向

```text
cmd/*  ──▶  server / client / cairnkv（公开 API）
server ──▶  cairnkv（公开 API） + proto
client ──▶  proto
cairnkv ──▶ internal/engine ──▶ internal/{wal, memtable, sstable, manifest, compaction, cache, filter, keys, metrics}
internal/* ──▶ vfs（公开的文件系统抽象，自身不引用任何 internal 包）
examples ──▶ cairnkv（公开 API）
test    ──▶ 任意包
```

禁止的依赖：

- `internal/*` 引用 `server`、`client`、`proto`、`cmd`
- `server` 或 `client` 引用 `internal/*`
- `internal` 下的底层包（如 `wal`）引用更高层的包（如 `engine`）
- `vfs` 引用 `internal/*`

可以在持续集成中用简单的导入检查脚本保证这些规则。

### 6.3 命名规范

| 对象 | 规则 | 示例 |
|------|------|------|
| 模块路径 | `github.com/LystranG/cairnkv` | — |
| 包名 | 全小写、短、单数、不含下划线 | `wal`、`sstable` |
| 导出类型 | 名词，表达职责 | `Options`、`Iterator` |
| 接口 | 以行为命名；仅一个方法时可用“-er” | `Compactor`、`FileSystem` |
| 错误 | 以 `Err` 开头的哨兵错误，或带上下文的包装错误 | `ErrNotFound`、`ErrCorruption` |
| 测试文件 | 与被测文件同目录，`*_test.go` | `wal_test.go` |
| 数据文件 | 固定前缀 + 递增编号，位数固定 | `000012.wal`、`000034.sst` |
| 元数据文件 | 固定前缀 + 编号 | `MANIFEST-000001` |
| 标记文件 | `marker.<名称>.<迭代号>.<值>` | `marker.manifest.<迭代号>.MANIFEST-000001` |
| 目录锁 | 固定文件名 | `LOCK` |

### 6.4 数据目录布局

```text
<data-dir>/
├── LOCK                                     # 进程独占标记
├── marker.format-version.<迭代号>.<版本>     # store 级格式版本（打开时最先读取）
├── marker.manifest.<迭代号>.MANIFEST-<编号>  # 指向当前 MANIFEST（取代 CURRENT，唯一真相来源）
├── MANIFEST-<编号>                           # 全量快照首记录 + 增量 VersionEdit
├── <编号>.wal                                # 预写日志
└── <编号>.sst                                # 不可变有序数据文件（未登记的在启动时清理）
```

WAL 与 MANIFEST 的文件头、SSTable 的 footer 都带魔数（`CairnWAL` / `CairnMAN` / `CairnSST`）与格式版本；所有块都带校验和。v1 不产生 `.tmp` 文件，但启动时仍会清理任何 `*.tmp`。字节级规格见 `docs/file-format.md`。

### 6.5 代码规范

- 使用 `gofmt` / `goimports` 统一格式，并启用 `go vet` 与静态检查。
- 每个包有包级注释，说明职责与不变量。
- 公开标识符必须有文档注释；持久化相关代码需写明“确认点”和“提交点”。
- 错误统一包装并保留上下文，用 `errors.Is` / `errors.As` 判断；数据损坏使用专门错误类型。
- 并发原则：谁拥有数据谁负责关闭；后台协程必须可被取消并能等待退出。
- 不使用全局可变状态；配置通过 `Options` 传入。
- 不在热路径使用反射与格式化字符串日志。

### 6.6 测试规范

| 类型 | 目的 | 位置 |
|------|------|------|
| 单元测试 | 各包内部行为 | 与代码同目录 |
| 对拍测试 | 随机操作序列，与内存参考实现对比 | `test/model` |
| 崩溃测试 | 在关键点注入故障，重启后校验一致性 | `test/crash` |
| 竞态检测 | 启用数据竞争检测跑并发用例 | CI |
| 模糊测试 | 对 WAL、数据文件解析等输入解析代码 | 各包 |
| 基准测试 | 复现实验数据 | `test/bench` |
| 崩溃一致性检查 | 在每个持久化操作前枚举崩溃状态，检查恢复结果是已提交批次的前缀 | `test/crash` |
| 确定性并发测试 | 用 `testing/synctest` 测组提交、停写与关闭，不依赖 sleep | 各包 |
| Linux 验证 | 本机 Docker 中跑全部测试；特权容器内在 ext4 / xfs 上跑持久化冒烟集 | `just test-linux` / `just test-linux-fs` |

所有会落盘的测试必须使用临时目录并在结束时清理。

### 6.7 文档与版本管理

- 每个持久化格式变更都要更新 `docs/file-format.md` 并提升格式版本；文档中的 hex 样例由测试逐字节校验。
- 每个对外语义（持久化档位、超时语义）在 `docs/durability.md` 中有明确表述。
- 使用语义化版本；公开 API 与协议变更需记录在变更日志。
- 分支策略：主分支保持可构建、可通过全部测试；功能在短分支完成。

## 7. Go 语言相关的设计注意点

这些是选择 Go 实现时需要提前决定的方向，不涉及具体实现。

| 主题 | 说明 |
|------|------|
| 文件同步 | 使用 `os.File.Sync` 将内容提交到稳定存储（darwin 上为 `F_FULLFSYNC`）；目录同步必须做，调用清单见 `docs/durability.md` [web:326] |
| 内存映射 | 标准库扩展包仅提供只读映射；需要写入或更细控制时要借助系统调用封装 [web:324]。第一期读路径不用 mmap，只在 `test/bench` 中做对照实验 |
| mmap 与调度 | 协程访问尚未在内存中的映射数据，可能因缺页而占用操作系统线程 [web:337]，因此“映射读”与“普通读”应同时提供并对比 |
| 并发模型 | 后台任务（刷盘、合并）使用受控数量的工作协程；前台读写通过明确的同步边界访问共享结构 |
| 内存与 GC | 大量小对象会增加 GC 压力；内存表与缓存需要通过容量上限与对象复用控制 |
| 平台差异 | 平台相关系统调用集中放在带构建标签的文件中 |

## 8. 验收标准

1. 写入若干数据后强制终止进程，重启后所有已确认写入可读。
2. 在“数据文件已写完、元数据未更新”的时刻注入崩溃，重启后无损坏文件被当作有效数据，数据不丢失。
3. 随机操作与参考实现对拍一致，且在数据竞争检测下通过。
4. 逐次同步 vs 分组同步、有无布隆过滤器、合并前后，三组对照实验数据齐全。
5. 远程客户端与嵌入式调用语义一致；服务端在磁盘变慢时不出现无限内存增长。
6. 时序示例仅依赖公开 API 即可运行，无需修改引擎。
7. 依赖检查通过：核心引擎中不存在对网络层的引用。

## 10. 风险与对策

| 风险 | 对策 |
|------|------|
| 合并逻辑范围膨胀 | 第一期只实现一种策略，其余以接口预留 |
| 平台文件系统语义差异 | 以 Linux 为验证基准，明确写入文档 |
| 网络层反向污染引擎 | 依赖规则 + 导入检查 |
| 过早追求映射读 | 先用普通读取，映射作为可对比实验 |
| 扩展承诺过大 | 只承诺有序 KV 上的有限结构，示例只做一个 |
| 范围蔓延到分布式 | 复制类功能作为可选实验，不进入验收必须项 |
| 规格与代码漂移 | 格式文档中的 hex 样例由测试逐字节校验；持久化确认点在代码中标注编号，由测试核对 |
