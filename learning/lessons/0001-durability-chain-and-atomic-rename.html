1. 三层楼：write 返回时，数据在哪

先把"写成功"拆开。一次 write() 至少要穿过三层，每层的"成功"含义不同：

应用缓冲例如 Go 里 bufio.Writer 的内存。进程崩溃就丢。
↓ write() 系统调用返回
内核页缓存page cache。进程崩溃不丢，断电/内核崩溃会丢。
↓ fsync() 返回
持久介质断电后仍在（前提是 fsync 被正确实现，第 2 课细讲 macOS 的坑）。

OSTEP 的说法是：调用 write() 只是在告诉文件系统"将来某个时候把它写到持久存储"； 文件系统为了性能会在内存里攒 5 秒或 30 秒再下发。

出处：《操作系统导论》§39.6 用 fsync()立即写入（英文 v1.10 为 §39.7）。

数据库要的是确定性，所以有 fsync(fd)：把这个文件的全部脏数据强制刷到磁盘，刷完才返回。

2. 陷阱：文件内容 ≠ 文件名

一个"文件"在文件系统里其实是两样东西：inode（内容 + 元数据）和目录里的一条目录项（名字 → inode）。 目录本身也是一个文件，它的内容就是这些目录项。

于是 fsync(f) 刷的是 f 的 inode 和数据，不保证"f 这个名字已经写进了父目录"。书中原文：

有趣的是，这段代码并不能保证你所期望的一切。在某些情况下，还需要 fsync()包含 foo 文件的目录。添加此步骤不仅可以确保文件本身位于磁盘上，而且可以确保文件（如果新创建）也是目录的一部分。毫不奇怪，这种细节往往被忽略，导致许多应用程序级别的错误。 ——《操作系统导论》§39.6 用 fsync()立即写入

新建文件、rename、删除，改的都是目录的内容。想让这些改动扛过断电，就要对目录打开一个 fd 再 fsync。

3. 原子替换协议

要把 CURRENT（LevelDB 里记录"当前是哪个 MANIFEST"的小文件）从旧内容换成新内容，又不允许崩溃后看到"半个文件"，经典做法是：

fd = open("CURRENT.tmp", O_CREAT|O_WRONLY|O_TRUNC)
write(fd, newContent)       // ① 新内容进页缓存
fsync(fd); close(fd)        // ② 新内容落盘
rename("CURRENT.tmp", "CURRENT")  // ③ 原子换名
fsync(dirfd)                // ④ 换名这件事落盘

每一步各有用处：

  • ③ rename 是原子的：书中说，若在 rename 过程中崩溃，文件要么是旧名字、要么是新名字，不会出现中间态。《操作系统导论》§39.7 文件重命名。原文："它（通常）是一个原子（atomic）调用"，注意那个"通常"。
  • ② 必须在 ③ 之前：原子性只管"名字指向谁"，不管"被指向的内容到盘了没有"。在一些文件系统上，rename 可能先于 tmp 的数据被持久化，崩溃后 CURRENT 就指向一个空的或半截的文件，旧版本也已经没了。
  • ④ 必须在 ③ 之后：rename 返回成功只说明"内核里已经换名"，不说明换名已持久。没有 ④，重启后看到的可能仍是旧的 CURRENT，这种情况合法，不算损坏，但也就谈不上"已确认"。
各文件系统在"什么操作会被重排"上差异很大，见 Pillai et al., OSDI 2014；他们在 11 个应用里找到 60 个崩溃漏洞，LevelDB 也在其中。通俗版：Dan Luu, "Files are hard"。

不要往回翻，凭记忆排序。排错时会告诉你崩溃后具体会出什么事。

5. 检验

Q1. write() 成功返回，最多能保证数据到了哪里？

write 只把数据交给内核（page cache）。进程崩溃不丢，断电会丢。要过下一层得靠 fsync。

Q2. 新建文件 f，write(f) 与 fsync(f) 都成功，随后立刻断电。重启后最可能出现的"坏情况"是？

fsync(f) 刷的是 f 的 inode 和数据；"f 这个名字"是父目录的内容。父目录没 fsync，目录项就可能没落盘。

Q3. foo 已存在，执行 rename(tmp, foo)，rename 进行中断电。重启后 foo 是？

rename 对崩溃是原子的（《操作系统导论》§39.7，"通常"）：要么旧名字、要么新名字。是不是新版本取决于 ④ 有没有做完。

Q4. 原子替换协议里，为什么 fsync(tmp) 必须放在 rename 之前？

rename 只保证"名字切换"原子，不保证被指向的内容已到盘。先 rename 再刷数据，断电后可能换上一个空文件，旧版本也已被替换。

Q5. LevelDB 在把 MANIFEST 刷盘之前先 SyncDirIfManifest()。它防的是哪种崩溃后状态？

这就是 D3：新 SST 的目录项必须先持久，MANIFEST 才能引用它。否则重启后元数据指向一个"目录里没有"的文件。

Q6. 合并删除旧 SST 之后再 fsync 一次目录（D4），主要为了？

unlink 改的也是目录内容。不 fsync 目录，重启后旧文件可能"复活"；恢复逻辑最好能确定地知道哪些文件存在。

展开参考答案

rename 改的是父目录的内容（目录项），而目录也有自己的页缓存。rename 返回成功意味着：内核中名字已经切换，之后的 open 能看到新文件； 且在崩溃面前它是原子的，不会出现半个名字。它不意味着切换已经持久：断电后可能回到旧名字。只有对目录 fsync 返回后， 这次切换才扛得过断电。另外，rename 也不对 tmp 的内容负责，所以 rename 之前还得先 fsync(tmp)。
